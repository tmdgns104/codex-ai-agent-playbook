상태: **APPROVED - READY FOR IMPLEMENTATION**

## 목적

Capability Registry 전체 본문이나 외부 Skill 내용을 LLM Context에 넣지 않고, 짧은 metadata만 사용해 현재 Task에 필요한 최소 Capability 후보를 결정론적으로 추천합니다.

이 Task는 **selection / recommendation only** 입니다.

실제 Skill 활성화, MCP 연결, Agent spawn, credential 사용, 외부 write는 하지 않습니다.

## 핵심 원칙

1. zero-capability 허용
2. 전체 선택 수 기본 최대 3개
3. MCP 최대 1개
4. Agent 최대 1개
5. Skill/CLI/REST보다 MCP와 Agent 선택 임계값을 높게 유지
6. deterministic metadata matching을 우선
7. LLM router 호출 없음
8. Capability 본문/SKILL.md를 routing 입력으로 사용하지 않음
9. 동일 입력 + 동일 Registry는 동일 결과
10. 선택 이유와 score를 출력해 사람이 검토 가능해야 함

## Allowed

- `harness/router/capability_router.py`
- `harness/router/scoring.py` 또는 동등한 소형 deterministic scoring 모듈
- router focused tests/fixtures
- Registry metadata의 routing에 꼭 필요한 최소 schema 확장
- Harness Audit의 router syntax/fixture coverage 유지
- `MANIFEST.txt` 갱신
- V8.1 Task/문서 상태 갱신

## Forbidden

- `.codex/AGENTS.md` 확대
- Capability 본문 자동 로드
- `.agents/skills` 동적 복사/삭제
- MCP config 수정
- MCP 서버 설치/기동
- Agent spawn
- network 호출
- credential 접근
- external write
- database write
- production/destructive action
- LLM/API 기반 semantic router
- 기존 V8 Quality Gate의 PASS/FAIL/UNVERIFIED 계약 변경

## 입력 계약

최소 CLI:

```cmd
python harness\router\capability_router.py --root . --task "<task text>"
```

선택적으로 JSON 출력:

```cmd
python harness\router\capability_router.py --root . --task "<task text>" --json
```

P0에서는 Task text가 필수입니다.

Repository path/file signal 사용은 deterministic하게 구현 가능한 경우에만 추가하며, 구현 복잡성을 키우면 후속 Task로 분리합니다.

## 출력 계약

사람이 읽는 기본 출력 예:

```text
Codex Playbook Capability Router
Task: FastAPI JWT 인증 오류를 수정하고 테스트해

SELECT     security-review       score=12 profile=STRICT
SELECT     testing               score=8  profile=STANDARD
SELECT     root-cause-debugging  score=7  profile=STANDARD

PROFILE    STRICT
COUNT      3
RESULT     ROUTED
```

선택할 Capability가 없으면:

```text
COUNT      0
PROFILE    MINIMAL
RESULT     NO_CAPABILITY
```

Router의 `RESULT`는 Repository 작업 완료 여부가 아닙니다.

## 추천 Score 구조

정확한 상수는 focused test로 조정할 수 있으나 다음 우선순위를 지킵니다.

### Positive signal

- trigger phrase exact match: 가장 높은 가중치
- trigger token match
- domain match
- summary token overlap: 낮은 보조 가중치

### Cost / risk penalty

- context_cost가 클수록 소폭 penalty
- MCP는 Skill/Wrapper보다 높은 selection threshold
- Agent는 가장 높은 selection threshold
- sensitive permission capability는 자동 활성화가 아니라 approval-required metadata로 표시 가능

### Type threshold 원칙

대략적인 상대 관계:

```text
skill / cli-wrapper / rest-wrapper
    < mcp
    < agent
```

threshold 숫자는 구현 테스트에서 고정합니다.

## Profile aggregation

선택된 Capability 중 가장 강한 `recommended_profile`을 최종 추천 Profile로 사용합니다.

```text
minimal < standard < strict
```

선택 0개면 `MINIMAL`.

## Tie / conflict rule

1. score 높은 순
2. score 같으면 context_cost 낮은 순
3. 그래도 같으면 risk 낮은 순
4. 그래도 같으면 capability id lexical 순

동일 입력 결과가 항상 같아야 합니다.

## Selection cap

기본:

```text
total selected <= 3
mcp selected <= 1
agent selected <= 1
```

cap을 채우기 위해 threshold 미달 Capability를 억지로 선택하지 않습니다.

## 권한 표시

이 Task에서는 activation을 하지 않지만, Router 출력에 다음 정보는 노출할 수 있습니다.

```text
approval: none | required
```

다음 permission 중 하나라도 있으면 기본적으로 `required` 후보로 취급:

- `credential_access`
- `external_write`
- `database_write`
- `destructive`
- `production`

`network`, `browser_control`, `local_write`, `process_exec`는 V8_1_CAPABILITY_POLICY 기준으로 별도 policy task에서 최종 activation gate를 적용합니다.

## Focused Test 최소 시나리오

1. trivial typo/README 문구 -> 0 capability
2. JWT/auth -> `security-review`
3. failing pytest/regression -> `testing` 및 필요 시 `root-cause-debugging`
4. API 최신 문서/version 확인 -> `documentation-lookup`
5. GitHub PR/push -> `github-ops`
6. bug/root cause -> `root-cause-debugging`
7. refactor/diff review -> `code-review`
8. 여러 신호가 있어도 total <= 3
9. synthetic MCP 후보는 낮은 약한 신호에서 선택되지 않음
10. synthetic Agent 후보는 MCP보다 더 높은 임계값을 요구
11. 동일 score tie-break deterministic
12. selected capability profile aggregation

## Acceptance Criteria

1. Registry validator를 통과한 metadata만 사용
2. Capability 본문 파일을 열지 않아도 routing 가능
3. zero-capability 시나리오 PASS
4. 최대 selection cap PASS
5. MCP/Agent higher-threshold test PASS
6. deterministic tie-break PASS
7. JSON 출력이 machine-readable
8. 기존 Harness Audit PASS
9. STRICT Quality Gate + Harness Audit PASS
10. 테스트 후 working tree clean
