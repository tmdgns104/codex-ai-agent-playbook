## 목표

V8.4의 목표는 pinned external Skill snapshot 전체를 runtime authority로 직접 사용하지
않고, 검증·승인 가능한 atomic knowledge unit으로 변환하여 task별로 필요한 context만
선택하는 것입니다. 이 과정은 provenance, permission, budget, canonical hash, session
isolation과 cleanup/quarantine을 보존해야 하며 기존 Router, Registry, activation, Skill
Materializer와 launcher의 책임을 침범하지 않아야 합니다.

현재 Release Candidate는 실제 runtime 통합 전의 control-plane 계약과 결정론적 구현을
정리한 상태입니다. 실제 Codex에 context를 전달하는 release가 아닙니다.

## 전역 적용하지 않는 이유

결정론적 unit test와 fake backend conformance는 내부 계약의 일관성을 보여주지만 실제
Codex가 context를 분리된 channel로 정확히 소비한다는 사실은 증명하지 못합니다. 이 상태에서
global launcher, Registry 또는 AGENTS에 연결하면 다음 위험이 있습니다.

- task/context concatenation 또는 duplicate injection
- unsupported backend에서의 silent fallback
- permission gate downgrade
- DRAFT Definition의 사실상 자동 활성화
- 고정 fixture 성능을 일반 사용 성능으로 오인
- stable V8.2 설치 경로와 experimental control plane의 혼합

따라서 context 비용 감소나 Wave 2 fixture PASS만으로 rollout gate를 열지 않습니다.

## Rollback 방향

현재 V8.4는 stable runtime에 연결되지 않았으므로 운영 rollback은 필요하지 않습니다.

- 안정 사용자는 `main`의 V8.2 설치·업데이트 경로를 계속 사용합니다.
- experimental branch를 `main`에 병합하지 않으면 V8.4는 활성화되지 않습니다.
- RC 문서나 isolated evaluation 구성요소를 되돌릴 때도 V8.3 Evidence와 V8.4-001~006
  task/report를 삭제하거나 수정하지 않습니다.
- Registry, Router, launcher, global AGENTS에 대한 역변경은 하지 않습니다. 이번 작업에서
  해당 구성요소를 변경하지 않았기 때문입니다.
- DNN 변경을 보존하는 `stash@{0}`는 rollback 대상이 아니며 유지합니다.
- 향후 실험 실패 시 raw external Skill 또는 launcher v1로 silent fallback하지 않고
  V8.2 current path를 명시적으로 유지합니다.
